# Hackathon requirements checklist

Extracted independently from the official page snapshot (`docs/reference/hackathon_page.md`) and the 13
practice cases (`docs/reference/hackathon_practice_cases.json`) on 2026-10-10. The **Requirement** and
**Source** columns come from the page. The **Consequence for the builder** column is **our reading [I]**,
not an official rule. The kit and organiser emails override this file.

## Objective (10)

| # | Requirement | Source | Consequence for the builder [I] |
|---|---|---|---|
| 1 | The deliverable is a builder program that creates phone agents on Freya. Only the phone agents it creates are scored. | hackathon_page.md L22, L66-L68: builder reads a brief, creates the phone agent; organisers score that phone agent | Put the effort into a program whose output (a Freya workflow) passes cases. The builder's code is checked only for reproducibility, honesty of the trace and build time. |
| 2 | Domain: a bank phones customers who are late on a payment. The agent identifies the right person, states what is owed and records when they will pay. | L39: phone late customers, check who is on the line, say what is owed, record when they will pay | Every generated workflow must cover right-party contact, identity check, disclosure only after verification, negotiation of amount and date, recording through the bank tools, and closing. |
| 3 | Hidden briefs are the same kind of call with different rules: other identity questions, other limits and deadlines, another outcome table, another calendar. | L82: same kind of call, different rules (identity questions, limits/deadlines, outcome table, calendar) | At build time, extract from the brief text a structured config: identity questions and retry rules, amount floors and limits, date bands and deadlines, outcome and reason codes, holidays and business days. | 4 | Final briefs are hidden so that a builder tuned to the public briefs does not win. The builder must read a brief it has never seen. | L98: hidden so a builder tuned to the two public briefs does not win | Test generalisation by building from rewritten or perturbed versions of Brief A/B (new values, new holidays, renamed codes, messy format), not only from the originals. |

| 6 | Calculations such as business days can run as code instead of being left to the model. | L108: business days etc. can run as code instead of being left to the model | Generate code nodes for date maths (deadlines from now, holidays, weekends, next business day, weekday names, parsing 'Friday the sixteenth') and amount checks. ## Scoring (12)

| # | Requirement | Source | Consequence for the builder [I] |
|---|---|---|---|
| 23 | Only the phone agents are scored, and rank comes from their score. | L92: only the phone agents are scored | Builder elegance has no value in itself. Pass rate is everything, then the tie-breaks. |
| 24 | A case passes only when all three checks pass: outcome (bank records), policy and honesty (transcript, judged by a model). There is no partial credit. | L94, L150, L154: three checks all must pass; outcome from records; policy and honesty by judge model | One wrong phrase, an early disclosure or an extra tool write fails the whole case. Prompts must enforce required statements and forbidden content strictly. |
| 25 | The scorer reads the mock bank's record, not what the phone agent says it did. | L140: scorer reads that record, not what the phone agent says it did | Verbal agreement without the correct tool call counts for nothing. Arguments (product_id, amount, date, queue, reason) must be exactly right. |
| 26 | The bank API does not enforce the brief. It records promises on holidays or below the minimum without complaint. | L152: bank API records a promise on a holiday or below minimum without complaint | Validate in the workflow before create_promise, ideally with a code-node guard (business day, not a holiday, within the deadline for that product's band, amount at least the floor and at most the past due). |
| 27 | A correct refusal counts. On a disputed debt the passing outcome is a recorded dispute and no promise; pushing for a promise anyway fails. | L156: dispute -> recorded dispute, no promise; pushing for a promise fails | Build a dispute branch that stops negotiation and records the dispute as the brief and tool API define it. Same pattern for other no-promise outcomes. |
| 28 | Score = cases passed / 60: 2 hidden briefs, 30 customers each. Each case runs 3 times and passes only if all 3 pass. | L162-L170: 30 customers per brief, 3 repetitions all must pass, score = passed/60 | Consistency dominates: a 90%-reliable case passes about 73% of the time. Minimise LLM freedom with code nodes, narrow step prompts and explicit routes. Self-test with repetitions. |
| 29 | Hidden customers have one to three products and calls happen on several calendar days. | L164: 30 per brief, 1-3 products, several calendar days | All date logic must be relative to now (weekday, tomorrow, Friday, deadlines). Both hidden agents need multi-product handling; nothing may assume Wednesday 14 Oct. |
| 30 | Hidden customers talk like people: numbers in two parts ('463...' then '51'), corrections, off-topic talk, questions back, amounts and dates in words. | L166: number in two parts, corrections, other topics, question back, amounts/dates in words | Prompts must wait for complete answers before calling verify_identity, take the latest correction, answer briefly and return to the flow, and normalise spoken amounts and dates (preferably in code). |
| 31 | Promises are compared as exact tuples (product_id, amount, date). | L184-L186: promises [('p1', 1250.0, '2026-10-27')], expected [('p1', 1250.0, '2026-10-23')] | Use the exact amounts from get_account (e.g. 637.5, 2125.1), ISO YYYY-MM-DD dates and product ids from get_account. Rounding or a one-day error fails. |
| 32 | The expected record per case has outcome, reason, promises, notes, callbacks and transfers. | hackathon_practice_cases.json 'expected' keys: outcome, reason, promises, notes, callbacks, transfers | Each of these ledgers must match, so avoid unrequired writes (e.g. no add_note where expected notes are []). Set outcome and reason exactly as the outcome table says. |
| 33 | Outcome and reason values seen in practice: promise/null, not_reached/callback, not_verified/failed, no_promise/hardship, paid/null, transferred/restructuring. Note reason 'refused', transfer queue 'restructuring'. The page also mentions a recorded dispute. | hackathon_practice_cases.json expected.outcome/reason across PUB-01..13 | Hidden briefs get 'another outcome table' (L82), so outcome/reason codes must be read from the brief and tool API enums, not from this list. |
| 34 | Results vary: the same phone agent can pass a case in one run and fail it in the next. | L192: same agent can pass in one run and fail in the next; use --reps 3 | Judge changes with --reps 3, not single runs. Prefer designs that move decisions from the LLM into routes and code. |
