# Direction review, 2026-10-10 ~17:00 UTC

Four read-only reviewers (submission, generalisation, scoring, rules) compared the live page (`docs/reference/hackathon_page_live_2026-10-10.md`) with the repo at 3a55e6d. Each finding was re-checked by a skeptic; the main session re-verified gaps 1-3 (llm.py:24-27 has no default model; spec-a and raw-a extracted max_products=1; render.py:17 caps opening 8 / third_party 12 / identity 20).

## Verdict

Yes, the direction is right. The builder matches what the page asks for. It takes one brief file plus one tool API file. It runs on the standard library only, calls only the kit's bank tools and does not touch the phone-agent model. Builds take about 2 to 3 minutes, and the trace has every part the Submit tab lists. It also handles raw bank material: the raw-a brief, built from a mail, a policy, a memo and a code list, scored 10/10 at 3 reps. The weak spot is not the design but what we measure and how well the agent holds up under realistic customers. The final gives each hidden customer 3 runs, and a case only passes if all 3 do. Those customers talk "like people" and many have 1 to 3 products. Our good 3-rep numbers come from plain customers talking to the single-product agent. The setup we will actually submit has never cleanly passed 3/3: an agent covering 1 to 3 products, facing styled customers. Today's talkative regression (6/10) is explained by two confirmed causes: turn limits that end the call without a goodbye, and a fragment rule that makes the agent repeat its offers, which the judge counts. One more risk sits outside scoring: if we reach the top 10, the organisers re-run our builder, and today that run would crash without our OpenAI key and env vars, which would get the entry removed. Do these first, all before the Sunday freeze: gaps 1 to 3 (cheap, generic code fixes plus one email), then gap 4 (fix how we measure), then gaps 5 and 6 (measured fixes).

## Aligned with the page

- **Run command and input match the form.** `python3 builder/build.py {brief_path} {tool_api_path}` works with the standard library only, from a fresh clone (Python 3.10 guard, kit/freya.py committed). The v3 kit's freya.py, docs, tools and briefs are byte-identical to ours.
- **The trace covers the Submit table.** It has UTC START and END plus build_seconds, one MODEL line per call, a CREATED line with workflow id, agent id, steps and tools, and TEST lines. Keys are redacted by value, tracebacks included (trace.py:15-34), and scripts/check_secrets.py runs before commit.
- **The agent calls only the kit's tool API.** URLs come from the tool API file (toolapi.py:85-98). Code nodes and hooks make no network calls, and the exported workflow contains only freya-bank-mock URLs.
- **The platform rules hold.** The phone-agent model stays experimental-5, there is one Freya key, workflows are updated in place (8 of 200 slots used), there is no probing (runs go one at a time), and exports come from the same build run.
- **Builds are fast:** 102 to 212 s with 2 or 3 model calls, which helps the build-time tie-break.
- **Raw-material briefs work.** raw-a (mail, policy, memo, code list) scored 10/10 at 3 reps, memo amendments are listed in the trace, and the single-file clean and raw variants extract 3 products.
- **Nothing is hard-coded from the briefs.** Tool fields, enums, identity keys and formats come from the spec and the tool API. Dates use the `now` call variable. Deadlines, floors and dates are computed in code and checked over about 42 call days plus each holiday. test_no_brief_values.py guards against practice-brief values.
- **The gates and honesty rules work.** get_account runs only after the identity check passes. get_account, close_call and transfer run in code, with close_call last and only once. "Recorded" is said only after a real success. The full amount is offered first, so tie-break 1 is not undercut.
